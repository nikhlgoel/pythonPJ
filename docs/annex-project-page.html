ANNAnnex
vector search engine · python 3.10+ · apache-2.0

A vector database engine, built from the byte layout up.

Annex is an embedded, transactional, vector-native search engine written from scratch in Python. No FAISS, no hnswlib, no SQLite — NumPy is the only runtime dependency. Every layer a production vector database actually needs is implemented here and measured: the graph index, the compression, the write-ahead log, the snapshot isolation, the lexical index, the query planner, the consensus protocol.

01  The problem

Vector databases are shipped as black boxes

You call add() and query(), you get results back, and you have no way to answer the questions that actually decide whether a retrieval system works: why did the engine pick those neighbours, what did it skip, how much recall did the filter cost you, and what would a different index have returned for the same query last Tuesday.

Annex is built on the opposite premise. Every mechanism is explicit, readable and inspectable — and the two things black boxes hide most are surfaced as first-class API: the query plan is returned with every result, and a snapshot is a value you can hold, so "what would this query have returned before last week's re-index?" is a question the engine can answer. 

# the query plan comes back with the results, like EXPLAIN in a relational database
>>> papers.search(q, k=10, filter={"venue": "NeurIPS"}).plan
{'strategy': 'exact_scan',   # ... not the graph. here is why:
 'live': 1200,               # 1,200 live vectors
 'selectivity': 0.1,        # the filter keeps ~10% of them
 'estimated_survivors': 120,
 'scan_cost': 10.0,          # cost in distance-computation equivalents
 'graph_cost': 1030.4,       # the graph would reject most nodes it visits
 'reason': 'selective filter makes a pre-filtered scan cheaper'}

02  How it works

Six layers, one address space

The design decision that holds the whole engine together is small and boring: every document version gets a dense integer key. The graph, the inverted index, the version table and the storage engine all address that same integer, so nothing on the hot path does string hashing or dictionary lookups, and a filter predicate is cheap enough to evaluate inside the graph traversal rather than after it.

Read path flows left to right through the planner; the write path drops straight down into the log. A crash between any two boxes recovers to the last acknowledged write.

What one search() call actually does

1
Compile the filter. {"year": {"$gte": 2020}} becomes a Python closure plus a selectivity estimate — compiled once, then called per candidate.
2
Plan. The planner costs an exact scan against a graph traversal in distance-computation equivalents and picks one. Below ~2,000 live vectors, or under a selective filter, the scan wins — and the measurements below say it is right.
3
Traverse. Greedy descent through the upper graph layers, then a beam search of width ef on layer 0. Every expansion evaluates all unvisited neighbours in one vectorised call.
4
Apply visibility. A candidate enters the result heap only if born ≤ snapshot < dead and the filter passes. Rejected nodes are still traversed, so the graph never fragments under a selective filter.
5
Retrieve lexically. If a query string was supplied, BM25 runs over the same keys with the same visibility predicate.
6
Fuse. Cosine and BM25 live on incomparable scales, so Annex fuses ranks: RRF(d) = ∑ w / (60 + rank). No calibration, and it degrades gracefully when one retriever returns nothing.
7
Return the plan with the hits. Strategy, costs, selectivity, candidates scanned, and a sentence of English explaining the choice.

The consensus core is, unusually, deterministic: the Raft node has no threads and no clock of its own, so a five-node cluster with a network partition is an ordinary unit test rather than a flaky integration suite. The transport was then bolted on without touching the protocol — which was the point of building it that way.

  • Consensus — leader election, log matching with back-off hints, the leader-completeness commit rule
  • Log compaction — InstallSnapshot catches up a follower that has fallen behind the retained log; only applied entries may be folded away
  • Membership changes — one server at a time, adopted on append, so old and new majorities always overlap
  • Transports — a single JSON wire codec, an in-process transport, and an HTTP transport where an unreachable peer is a dropped packet rather than an exception

04  How good is it

Measured, not asserted

Every number below comes from make bench on 20,000 clustered 128-dimensional vectors, 200 queries, k = 10, single-threaded, with recall scored against exact brute-force ground truth on the same data. Queries are drawn near existing points, and the corpus is a mixture of Gaussians rather than uniform noise — uniform vectors flatter a graph index and real embeddings are clustered.

The y-axis is zoomed to 0.970–1.000 so the four HNSW settings are separable; the compressed-codes configuration (0.636) sits far below this window and is in the table above.

Three results worth reading twice

1. ef is a clean, monotone dial. Going from 0.977 to 0.997 recall costs 4.8× the latency, and recall saturates long before latency does. That is why ef is exposed per query, not just per collection: a "find me anything relevant" query and a "this had better be exhaustive" query should not pay the same price.

2. The exact scan really does win on small collections. At n = 4,000 the flat scan runs at 2,751 q/s against the graph's 2,025 — both at perfect recall. A single BLAS-backed pass beats a Python graph walk until the corpus is big enough to amortise the traversal. This is the entire justification for the query planner, and it is why small_collection_threshold defaults to 2,000 rather than to zero.

3. Product quantisation is a memory trade, and the page says so. Codes alone shrink the vector store 17× — 10.2 MB to 0.6 MB — and cost recall down to 0.636. Keeping the originals for the rerank stage restores 0.986. Sub-space granularity dominates: moving from 8 sub-vectors to 32 took recall from 0.61 to 0.97 at effectively the same memory.

05  Engineering quality

The tests are the specification

Correctness claims in this project are executable. "HNSW recall is high" is a test that measures recall against exact ground truth. "A torn write cannot corrupt the database" is a test that appends garbage to a live WAL and reopens it. "A minority partition cannot commit" is a test that partitions a simulated five-node cluster.

What is guaranteed, and what is not

✓ Guaranteed

  • An acknowledged write is in the log before it returns; a crash recovers to exactly that point.
  • A torn or bit-flipped frame is detected by CRC and truncated, never silently applied.
  • Readers never block writers; a snapshot sees a consistent point in time.
  • flat results are exact; HNSW recall is tunable and measured, not assumed.
  • Committed entries survive leader changes — the commit rule is implemented, not approximated.

● Not claimed

  • This is pure Python and NumPy. Throughput sits one to two orders of magnitude below a SIMD C++ engine — the design is the artefact, not the constant factor.
  • Index build is the weak spot: 121 s for 20,000 inserts, because the neighbour heuristic runs per insert in Python. Phase 6 addresses exactly this.
  • Raft covers election, replication, compaction and membership changes over a live HTTP transport. Pre-vote, leadership transfer and read-index leases are not implemented.
  • One writer per collection. Concurrent readers scale freely.

06  Immediately next

Finishing Phase 5

Three pieces close distribution: an HTTP transport that carries the same AppendEntries and RequestVote messages the simulator already exercises; InstallSnapshot, so a follower that has fallen further behind than the retained log can be caught up with a segment file instead of a replay; and joint-consensus membership changes so nodes can be added without downtime.

Because the consensus core is a pure state machine, none of that work can change the protocol's behaviour — the transport moves bytes and the tested logic stays exactly as it is. That separation was the point of building it this way.
